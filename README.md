# CDC PostgreSQL → Kafka: SQL Polling vs Streaming Replication vs Competing Consumers (benchmark скорости)

## Что хотели сделать изначально

Пример CDC-решения для PostgreSQL (изначальная идея записи — через `pg_logical_emit_message()`) и benchmark **трёх подходов чтения** outbox → Kafka:

- **Polling** — работа со слотом через SQL-функции PostgreSQL: `pg_logical_slot_peek_changes()` читает изменения порциями, не двигая слот; после обработки позиция подтверждается через `pg_replication_slot_advance()`.
- **Streaming** — подключение к слоту репликации по протоколу логической репликации через Npgsql (по образцу subscription).
- **Competing consumers** — таблица-очередь без логического слота: несколько независимых читателей (воркеров) в одном сервисе параллельно и независимо разгребают очередь — `DELETE … WHERE id IN (SELECT id … FOR UPDATE SKIP LOCKED LIMIT n) RETURNING …`; количество воркеров задаётся конфигурацией.
- **Failover-слоты PostgreSQL 17** — новая возможность версии: logical-слот с `failover=true` синхронизируется на стендбаи и переживает promotion (до PG17 логический слот жил только на primary и терялся при смене лидера — CDC не мог продолжить чтение после failover).

## Что получилось в итоге

Всё, что задумали, реализовано: три подхода чтения работают на одном стенде, прогоняются одним harness'ом (одинаковые сценарии нагрузки, вердикт независимого валидатора — 0 потерь) и сравниваются построчно в таблице результатов.

- **Запись — через outbox-таблицу** (`public.outbox_messages`): Writer делает INSERT + DELETE в одной транзакции (режим `insertDelete` — дефолт: таблица всегда пустая, сообщение живёт в WAL); для arm competing есть режим `insertOnly` — строки остаются в таблице, их разбирает читатель. От `pg_logical_emit_message()` отказались: плагин `pgoutput` не передаёт logical messages ни в одной версии PostgreSQL (проверено на 17.2 и 18.4), а `test_decoding`, который их видит, не подходит для production.
- **Чтение Polling** — `pg_logical_slot_peek_binary_changes()` + `pg_replication_slot_advance()` через SECURITY DEFINER-обёртки `cdc.peek_outbox_changes()` / `cdc.advance_outbox_slot()`, вызываются от пользователя `sys_app` **без** атрибута REPLICATION (прямой вызов этих функций требует привилегии REPLICATION, которую прикладному пользователю не даём).
- **Чтение Streaming** — чтение напрямую из слота репликации через Npgsql (`PgOutputReplicationSlot`, pgoutput) от пользователя `sys_replication` с атрибутом REPLICATION.
- **Чтение Competing** — как и задумано: N независимых воркеров в одном сервисе (по умолчанию 10 × пачка 10000 — tuned-конфиг с 2026-11-12, цели см. «Целевые показатели competing»; до этого 5×2000) забирают пачки `DELETE … FOR UPDATE SKIP LOCKED … RETURNING` от отдельной роли `sys_drainer`, COMMIT только после Kafka delivery пачки (at-least-once), слот не используется вовсе.

## Результаты прогонов

Условия (прогон 2026-11-12): публикация insert-only (`publish='insert'`), polling — размер peek-батча **10000**; competing — tuned-конфиг **10×10000** (kafka-чанк 10000, дефолт с 2026-11-12; цели и история тюнинга — раздел «Целевые показатели competing»); Writer подключается напрямую через HAProxy (мимо PgBouncer); каждая реализация на полностью пересозданном стенде; 5 сценариев, всего 4 125 000 сообщений на реализацию (s5 — pre-seeded backlog 4M), 0 потерь, 0 дубликатов.

### Сценарии

Каждый сценарий — прогон Writer'а: старт записи (t0) → Writer дописал все сообщения (t1) → валидатор (независимый консьюмер Kafka) увидел всё сообщение прогона в топике (t2). Перед сценариями идёт warmup-прогон, в результаты не входящий.

- **s1 — равномерная низкая нагрузка:** 30 000 сообщений со скоростью 50/с (~10 мин), размер 256 Б. Типовой «ровный» поток — замер steady-латентности.
- **s2 — равномерная высокая нагрузка:** 60 000 @ 200/с (5 мин), 256 Б. То же, но темп записи в 4 раза выше.
- **s3 — burst / backlog-drain:** 20 000 без rate limit — Writer вываливает пачку практически мгновенно, CDC разбирает её на пределе; короткий сценарий «на скорость выборки».
- **s4 — крупные сообщения:** 15 000 @ 50/с (5 мин), размер 4096 Б. Влияние размера тела на латентность и скорость.
- **s5 — max throughput, pre-seeded backlog:** 4 000 000 без rate limit пишутся при **остановленном** CDC; после завершения записи CDC стартует и дрейнит backlog в чистом виде — скорость записи Writer'а (напрямую через HAProxy, ~110–150 тыс/с) из измерения исключена, узкое место по построению — только CDC. Дрейн считается с момента старта CDC (бут контейнера учтён отдельно); слот за время простоя не инвалидируется, WAL (~3 ГБ) копится и выбирается после старта.

### Как читать таблицу

Один сценарий — три строки (реализации рядом, сравнение построчно). Колонки:

- **Реализация** — вариант CDC: polling (`pg_logical_slot_peek_binary_changes` + `pg_replication_slot_advance`), streaming (репликация) или competing (таблица-очередь `DELETE … FOR UPDATE SKIP LOCKED … RETURNING`, без слота).
- **Скорость (overall)** — средняя скорость доставки по всему окну сценария: доставлено сообщений / (t2 − t0). В s5 (pre-seeded backlog) — средняя скорость самого дрейна (окно от старта CDC до полной доставки): фаза записи Writer'а в измерение не входит.
- **Пик** — максимум скорости доставки между соседними сэмплами счётчика доставки CDC (сэмплер опрашивает раз в ~1.5–2 с, т.е. пик усреднён по этому интервалу).
- **e2e mean / e2e p95** — сквозная латентность одного сообщения: от `created_at` (проставляет Writer в момент создания) до Kafka delivery report (подтверждение записи брокером, acks=all). mean — среднее за сценарий, p95 — 95-й перцентиль.
- **Дрейн backlog** — сколько продолжалась доставка остатка: в steady-сценариях и s3 — после того, как Writer закончил запись (CDC успевает в темпе записи — ~100 мс; в s3 — фактическое время разбора пачки); в s5 (pre-seeded backlog) — с момента старта остановленного на время записи CDC (чистый дрейн, бут контейнера учтён отдельно в `cdcBootMs`).

### Целевые показатели competing (tuned 10×10000, зафиксировано 2026-11-12)

Дефолт с 2026-11-12 — **10 воркеров × drain-пачка 10000 × kafka-чанк 10000** (compose/.env/.env.example). Обоснование: пачка 10000 почти вдвое снижает per-row цену DELETE (12.75 против 23.2 мкс/строку при пачке 2000 — меньше транзакций на тот же объём), выровненный kafka-чанк убирает 4 из 5 produce-циклов на пачку (−9% дрейна), 10 воркеров на большой пачке ещё дают +15% (потолок DELETE при пачке 10000 выше — конкуренция дешевле). От старого дефолта 5×2000: дрейн 90.5 → 57.1 с (−37%), avg 44.1k → 68.4k (+55%). ### Выводы по s5 (что показала смена методики)

До смены методики s5 гонялся concurrent (400k, Writer и CDC работали одновременно) — сравнение со старыми числами:

- **Короткое окно завышало «устойчивую» скорость**: на 400k-прогоне competing avg 74.4k / streaming 63.4k / polling 24.7k; на длинном pure-drain 4M — 44.1k / 100.9k / 24.5k (competing тогда в конфиге 5×2000). У competing avg упал в 1.7 раза (burst-фаза маскировала деградацию на длинной очереди), у streaming — вырос в 1.6 раза.
- **Polling недооценивали по пику**: 39.1k на concurrent-прогоне против 65.8k на pure-drain — без конкуренции Writer'а за лидера peek/advance разгоняется вдвое.
- **Streaming — единственный, кто держит скорость на длинном окне** (100.9k avg в течение 40 с, пик 164k): на коротком окне он выглядел «примерно равным» competing (63k против 74k), на длинном — быстрее в 2.3 раза. Tuned competing (10×10000, с 2026-11-12) закрывает большую часть разрыва — 66.2k против 92.8k у streaming в прогоне 2026-11-12 (~1.4×), см. «Целевые показатели competing».
- **Ресурсный профиль при backlog-дрейне**: competing переносит нагрузку в postgres (CPU лидера 262%, память CDC 3.71 ГБ — 100k строк в полёте), слотовые arm'ы — в собственный процесс декодирования (CPU CDC max 451–636%, память 3.0–3.9 ГБ; CPU лидера 97–107%).

## Замечание: непотребляемый logical-слот не переживает failover

Документированное поведение PostgreSQL 17 ([§47.2.3 «Replication Slot Synchronization»](https://www.postgresql.org/docs/17/logicaldecoding-explanation.html#LOGICALDECODING-REPLICATION-SLOTS-SYNCHRONIZATION)), не баг.

**Что происходит.** Если слот никто не потребляет, его позиция на primary стоит на месте, а catalog_xmin стендбая уходит вперёд. Воркер синхронизации отказывается обновлять такую копию (`could not synchronize replication slot "outbox_slot" because remote slot precedes local slot`) — копия не достигает состояния `synced=true`, и при promotion она отбрасывается: слот исчезает на новом leader. Это защита от потери данных: promotion переживают только слоты, успевшие синхронизироваться.

**Вывод — некритично.** Работающий CDC потребляет слот непрерывно и подтверждает LSN после Kafka delivery, поэтому копия остаётся синхронизированной и переживает failover с сохранением позиции (проверено контролируемыми switchover'ами на стенде). Проблема актуальна только для простаивающего стенда без потребителя — там слот перед failover-экспериментом нужно продвигать вручную (`pg_logical_slot_get_binary_changes`; peek не продвигает).
