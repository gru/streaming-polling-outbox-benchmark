# CDC PostgreSQL → Kafka: SQL Polling vs Streaming Replication (benchmark скорости)

## Что хотели сделать изначально

Пример CDC-решения для PostgreSQL с записью через `pg_logical_emit_message()` и чтением двумя способами:

- **Polling** — работа со слотом через SQL-функции PostgreSQL: `pg_logical_slot_peek_changes()` читает изменения порциями, не двигая слот; после обработки позиция подтверждается через `pg_replication_slot_advance()`.
- **Streaming** — подключение к слоту репликации по протоколу логической репликации через Npgsql (по образцу subscription).
- **Failover-слоты PostgreSQL 17** — новая возможность версии: logical-слот с `failover=true` синхронизируется на стендбаи и переживает promotion (до PG17 логический слот жил только на primary и терялся при смене лидера — CDC не мог продолжить чтение после failover).

## Что получилось в итоге

- **Запись — через outbox-таблицу** (`public.outbox_messages`): Writer делает INSERT + DELETE в одной транзакции, таблица всегда пустая, сообщение живёт в WAL. От `pg_logical_emit_message()` отказались: плагин `pgoutput` не передаёт logical messages ни в одной версии PostgreSQL (проверено на 17.2 и 18.4), а `test_decoding`, который их видит, не подходит для production.
- **Чтение Polling** — `pg_logical_slot_peek_binary_changes()` + `pg_replication_slot_advance()` через SECURITY DEFINER-обёртки `cdc.peek_outbox_changes()` / `cdc.advance_outbox_slot()`, вызываются от пользователя `sys_app` **без** атрибута REPLICATION (прямой вызов этих функций требует привилегии REPLICATION, которую прикладному пользователю не даём).
- **Чтение Streaming** — чтение напрямую из слота репликации через Npgsql (`PgOutputReplicationSlot`, pgoutput) от пользователя `sys_replication` с атрибутом REPLICATION.

## Результаты прогонов

Условия: публикация insert-only (`publish='insert'`), polling — размер peek-батча **10000**; каждая реализация на полностью пересозданном стенде; 5 сценариев, всего 525 000 сообщений на реализацию, 0 потерь, 0 дубликатов.

### Сценарии

Каждый сценарий — прогон Writer'а: старт записи (t0) → Writer дописал все сообщения (t1) → валидатор (независимый консьюмер Kafka) увидел всё сообщение прогона в топике (t2). Перед сценариями идёт warmup-прогон, в результаты не входящий.

- **s1 — равномерная низкая нагрузка:** 30 000 сообщений со скоростью 50/с (~10 мин), размер 256 Б. Типовой «ровный» поток — замер steady-латентности.
- **s2 — равномерная высокая нагрузка:** 60 000 @ 200/с (5 мин), 256 Б. То же, но темп записи в 4 раза выше.
- **s3 — burst / backlog-drain:** 20 000 без rate limit — Writer вываливает пачку практически мгновенно, CDC разбирает её на пределе; короткий сценарий «на скорость выборки».
- **s4 — крупные сообщения:** 15 000 @ 50/с (5 мин), размер 4096 Б. Влияние размера тела на латентность и скорость.
- **s5 — max throughput:** 400 000 без rate limit — Writer завершает запись за секунды (замерено 67–108 тыс/с), CDC дрейнит образовавшийся backlog на пределе возможностей; узкое место по построению — сам CDC.

### Как читать таблицу

Один сценарий — две строки (реализации рядом, сравнение построчно). Колонки:

- **Реализация** — вариант CDC: polling (`pg_logical_slot_peek_binary_changes` + `pg_replication_slot_advance`) или streaming (репликация).
- **Скорость (overall)** — средняя скорость доставки по всему окну сценария: доставлено сообщений / (t2 − t0).
- **Пик** — максимум скорости доставки между соседними сэмплами счётчика доставки CDC (сэмплер опрашивает раз в ~1.5–2 с, т.е. пик усреднён по этому интервалу).
- **e2e mean / e2e p95** — сквозная латентность одного сообщения: от `created_at` (проставляет Writer в момент создания) до Kafka delivery report (подтверждение записи брокером, acks=all). mean — среднее за сценарий, p95 — 95-й перцентиль.
- **Дрейн backlog** — t2 − t1: сколько продолжалась доставка остатка после того, как Writer закончил запись. В steady-сценариях CDC успевает в темпе записи — это ~100 мс; в s3/s5 это фактическое время разбора накопленной пачки.

## Замечание: непотребляемый logical-слот не переживает failover

Документированное поведение PostgreSQL 17 ([§47.2.3 «Replication Slot Synchronization»](https://www.postgresql.org/docs/17/logicaldecoding-explanation.html#LOGICALDECODING-REPLICATION-SLOTS-SYNCHRONIZATION)), не баг.

**Что происходит.** Если слот никто не потребляет, его позиция на primary стоит на месте, а catalog_xmin стендбая уходит вперёд. Воркер синхронизации отказывается обновлять такую копию (`could not synchronize replication slot "outbox_slot" because remote slot precedes local slot`) — копия не достигает состояния `synced=true`, и при promotion она отбрасывается: слот исчезает на новом leader. Это защита от потери данных: promotion переживают только слоты, успевшие синхронизироваться.

**Вывод — некритично.** Работающий CDC потребляет слот непрерывно и подтверждает LSN после Kafka delivery, поэтому копия остаётся синхронизированной и переживает failover с сохранением позиции (проверено контролируемыми switchover'ами на стенде). Проблема актуальна только для простаивающего стенда без потребителя — там слот перед failover-экспериментом нужно продвигать вручную (`pg_logical_slot_get_binary_changes`; peek не продвигает).
